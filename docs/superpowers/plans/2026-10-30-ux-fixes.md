# UX fixes — native prompts, flows, Compare and the Chinese words

The maintainer: "treat users as users — programmers also need things simple and easy to
understand." An independent audit listed 19 places where Linyra's prompts, flows and Chinese
wording make the user work it out. Each was read again on `feat/1.7.0` (cfc3c31) before this
plan; all 19 are real. Where this plan does something other than the audit asked, it says why.

Files owned by other sessions are not edited here: the Log panel (`list.ts`, `toolbar.ts`,
`main.ts`, `html.ts`, `styles.css`, `repoPane.ts`, `logView.ts`, `branchSheet*`, `changesColumn.*`,
`filterModel.ts`), `src/ai/`, `src/webview/changes/*`, `src/webview/compare/sideTree.ts`,
`src/webview/commit/*`. What they need is sent to their session (end of this plan).

## One report for work across repositories (1, 9, 14)

Today `MultiRepo.report` says "Update Project: done in 0 of 5 repositories." when nothing was
behind, and files a repository that stopped on conflicts under "Left as they were", though it is
mid-merge or mid-rebase.

- `MultiResult` gains `stopped: {name, reason}[]`: a write that git left half-way (a merge or
  rebase stopped on conflicts). `each()` sorts a failure there when git's words say conflict.
- A pure `multiReport(kind, result, extra)` in `multiRepoModel.ts` writes the one notification,
  in groups, each named only when it has members:
  - **Updated / Merged / Checked out / Created / Tagged / Pushed** (the action's own verb)
  - **Already up to date** (Update; Check out says "Already on it")
  - **Stopped on conflicts — resolve or abort**
  - **Left as they were** (with the short why)
  - Nothing to do: "All 5 repositories already up to date."
- Level: information when nothing stopped or was left; warning otherwise, with a button
  **Open Source Control** when something stopped on conflicts.
- Used by Update Project, Branches Across Repositories, Tag Across, Push…, Compare's merge and
  Release.
- **Push…** (9): success is a notification, "Pushed 7 commits to 3 repositories." (was an 8 s
  status-bar line). The outgoing list reads up to 1000 commits (was 50) so the count is right.
- **Commit side bar, partial failure** (14): "Committed in acme-web, acme-api. Not committed in
  acme-libs: <why>. The message is kept: Commit tries the rest again." The repositories that
  committed are named; the error says Commit retries.

## Prompts that say what will happen (2, 3, 8)

- **Delete branch** (2). The prompt says what happens, not a rule: "The local branch is deleted.
  Its remote branch origin/feature/x stays." / "origin/feature/x is deleted on the remote origin.
  Local branches stay." When git refuses ("not fully merged", the normal case after a squash
  merge), Linyra counts the branch's commits that are on no other branch, remote branch or tag
  (`git rev-list --count <branch> --not --exclude=<branch> --branches --remotes --tags`, one
  process) and asks once more: "feature/x is not merged into main." / button
  **Delete Anyway (4 commits not merged anywhere)** → `git branch -D` (VS Code's
  `deleteBranch(name, true)` where it watches the repository).
- **Reset Current Branch to Here** (3). The confirmation names what leaves the branch:
  "4 commits leave main (2 already pushed to origin/main). Uncommitted changes are deleted."
  (Hard) / "… Their changes stay in your files, staged." (Soft) / "…, unstaged." (Mixed). A target
  off the branch also says what arrives ("main gets 3 commits from 1a2b3c4"). Two processes, in
  parallel: `rev-list --left-right --count HEAD...<sha>` and the same with `--not --remotes`.
  Pure `resetPrompt()` in `commitActionModel.ts`.
- **Merge / Rebase a branch** (8). Buttons **Merge** / **Rebase** (not "Continue", which is
  Continue Merge's word). Detail: "main gets 4 commits from feature/x; if files conflict the merge
  stops for you to resolve." / for rebase: "Your 2 commits on main are replayed on top of
  feature/x's 4; if files conflict the rebase stops for you to resolve." Nothing to take: an
  information message instead of a question. One `rev-list --left-right --count`. Pure
  `integratePrompt()` in `branchModel.ts`.

## Release… as one review form (4)

Today: notes read → Merge checklist → tag InputBox → push modal; Esc at the tag box ends it
silently after the merges.

One form, before anything runs, in an editor tab like the ai-settings session's Linyra AI page
(a `WebviewPanel`, VS Code Elements checkboxes, theme variables only):

```
Release develop into main
Merges develop into main in the ticked repositories, then tags and pushes main if you ask.

Repositories                                  ☑ acme-web   develop → main · 4 commits · main checked out
                                              ☑ acme-api   develop → main · 2 commits · working tree not touched
                                              Not offered: acme-libs (would conflict)
Tag on main (optional)      [ v1.4.0        ]  each repository's notes become its message
☑ Push main and the tag to each repository's upstream
▸ Release notes (copied when done)
                                                        [ Release ]  [ Cancel ]
```

- A small, general form (`formModel.ts` pure: fields, validation, values; `formPanel.ts` the
  panel; `webview/form/*` the page, own bundle `out/form.js`/`form.css`). Release and Tag Across
  both use it.
- `Ask.form(spec)` opens it; the integration suite answers it from the same queue with the
  values as JSON. The host checks every value again.
- Nothing runs until **Release**. Then: merge (no second checklist), tag, push, notes copied and
  opened, one grouped report. Cancel or closing the tab: nothing happened.
- `mergeIntoRight`'s planning moves into one `mergePlans()` both use.

## One working tree, one vocabulary (5)

- **Commit…** on the Uncommitted side and in the Changes view opens the Commit side bar with
  that repository's files checked (its tracked changes, as the side bar checks by default; other
  repositories unchecked) and the message box focused. No InputBox, no modals. `uncommittedActions.commit` goes.
- **Discard Changes** (放弃更改) everywhere, with Rollback's behavior: tracked files back to the
  last commit, a newly added file only leaves version control (kept on disk). New, untracked files
  are never deleted by it; **Delete…** is the command that deletes them, and it is now on the
  Uncommitted side and in the Changes view too (for new files). The Commit side bar's Rollback…
  becomes Discard Changes; its prompt is the one prompt (`discardPrompt` = today's
  `rollbackPrompt`, renamed).
- Changed from the audit: **Add to VCS / Remove from VCS** stay (they are the side bar's only
  words for tracking a new file; the side bar has no Stage), but read 加入版本控制 / 移出版本控制.

## Getting remote changes (6, 13)

- Kept: **Fetch All** and **Update Project…**. Update gains a third method, **Fast-forward
  only** (`git merge --ff-only @{upstream}`; a diverged repository is left as it was, named).
- **Fetch and Pull All** and **Pull All Repositories Behind** leave every menu and the Command
  Palette; their command ids stay registered (keybindings keep working).
- Pull All Behind's "diverged" warning no longer says "use a terminal": it offers
  **Update Project…**.
- Update Project remembers the method (first in the list next time). Each method has a 📌 button,
  "Always use this method (don't ask again)", which writes the new setting
  `linyra.updateMethod`: `ask` (default) | `merge` | `rebase` | `ffOnly`. Set to a method, Update
  Project runs without the question; the report says which method ran.

## Errors that say what to do (7)

"Branch action failed in {0}: {1}", "Commit action failed…" and "Stash action failed…" become
"Could not <action> <name> in <repository>: <why>. <what to do>." A pure `failureReason()` (moved
out of `updateReason`, which now calls it) maps git's common words:

| git says | Linyra says |
|---|---|
| rejected, non-fast-forward / fetch first | the remote has commits you do not have — Update Project, then push again |
| CONFLICT | files conflict — resolve them in Source Control, or abort |
| not fully merged | (handled by Delete Anyway) |
| would be overwritten, commit or stash | local changes to the same files — commit or stash them first |
| no upstream, no tracking information | it has no upstream branch — push it once to set one |
| Authentication failed, Permission denied, could not read Username | the remote refused the sign-in |
| Could not resolve host, unable to access | the remote could not be reached |

## Feedback and shorter chains (10, 11, 12, 15)

- **Branch actions** (10): one status-bar line each for push, pull, fetch, merge, rebase,
  delete and rename ("Linyra: pushed feature/x to origin/feature/x in acme-web.").
- **Tag Across Repositories…** (11): the form (above): Tag name, Message (optional), ☑ Push to
  each repository's remote (remembered), the repositories that already have the tag named. "Lightweight
  tag" is gone from the words: an empty message makes one, and the form says only "Message (optional)".
- **Stash Changes…** (12): one input box with an **Include new files** toggle button in its title
  (remembered). The ✨ AI button lives in `src/ai/`: the box is built here, and AI writes into it
  through a hook the ai-settings session is asked for (below); until it lands, the AI box keeps
  working as today with the remembered toggle value.
- **Check out a remote branch** (15): uses the same local name, no question (an existing local
  branch tracking it is checked out; one that tracks something else is an error that says to use
  New Branch from Here…).
- **Apply Patch…** (15): source first (file or clipboard), then the repository is inferred from
  the patch's paths (the ticked repository where every file the patch changes exists; the files
  are `stat`ed, no git process). Asked only when none or several fit, best fit first.

## Compare (16, 17, 18)

- **Merge** (16): a labeled button after the branch boxes, "Merge into main…" with the real name
  (◀ ▶ icons stay on the boxes). Disabled until two different branches are picked.
- **Empty states** (17): no pointers at unlabeled controls. A side whose files are all on both
  says "Every file this side changed is already on both branches." and offers a link
  **Show 3 files already on both**; Only Conflicts with none says so and offers **Show all files**.
  The page renders the link under the side's message (`compare/main.ts`, not `sideTree.ts`).
- **Stable toggle labels** (17): the funnel is "Hide Files Already on Both" with aria-pressed
  saying on/off (its title no longer flips to the opposite); Only Conflicts likewise.
- **Layout buttons** (18): their own keys, "Side by Side" / "Stacked" → 左右排列 / 上下排列 (they
  borrowed the Log's "Side-by-side Layout", 左右排列日志与更改).

## Naming (19)

- Repo List: "Hide from the Log" → **Untick** (取消勾选); "Exclude from Linyra" → **Always Hide
  (Settings)** (永久排除（写入设置）). Changed from the audit: no "…" — the command asks
  nothing (it offers Undo afterwards), and "…" means a question follows.
- Search toggles (owned by the Log session): sent to it — keep "Match Whole Word" (全字匹配), rename
  "Match All Words" to **Require Every Word** (每个词都要出现) with the tooltip "Require Every Word
  (in any order)".
